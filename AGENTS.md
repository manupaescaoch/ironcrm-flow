# Architecture Decisions
- Send Telegram payables payment data as a separate reply to its reminder and persist the reminder ID before sending the payment data, so copying excludes the summary and retries do not repeat a successful reminder.
- Keep BTG DDA consent state and encrypted OAuth tokens in server-only tables, scoped by unit CNPJ; request only read-only DDA scope and block synchronization until the official list operation and pagination are verified, so banking credentials and unverified imports never reach the browser or payables.
- Apply the shared manager messaging policy before operational channel fallback and disable legacy manager WhatsApp summary handlers, so manager notifications cannot silently revert from Telegram to WhatsApp.

- Keep `gestao_metas.meta_alunos_mes` as the backward-compatible minimum monthly target and store the optional stretch target in `supermeta_alunos_mes`, because existing reports and integrations depend on the legacy column.
- Run the unit-scoped manager FU digest inside the existing operational-summary cron callback, with a Recife weekday guard and atomic per-unit/day/part send claims, to avoid a second polling schedule and duplicate Telegram broadcasts.
- Use the shared pure FU business-day date module for frontend and Telegram counts, and normalize persisted pending deadlines in the database, so weekend deadlines have one effective date and one owning week.- Telegram Contas a Pagar intake runs inside the single telegram-webhook (chat_id must match the connected contas_pagar group, gated by app_config.contas_pagar_telegram_ativo) and writes only to the existing contas_pagar table with conferencia_status, because one bot has one webhook and there must be no parallel payables module.
- Telegram payables reminder buttons (PAGO/REAGENDAR) are handled in the same telegram-webhook via _shared/contasPagarBotoes.ts; rescheduling writes data_pagamento_prevista and never changes data_vencimento, because the bank due date must be preserved.
- Bank reconciliation reads EVO OS transactions pushed to the evo-os-transacoes function (mirror table transacoes_bancarias_evo_os, keyed by EVO OS id) and only links them to existing contas_pagar rows; conciliacao_status is independent of payment status, because EVO OS is the bank source of truth and no second cash entry may be created.
- Telegram document CONFIRMAR/EDITAR buttons live in _shared/contasPagarConferenciaTelegram.ts inside the single telegram-webhook; edits are staged in contas_pagar_telegram_edicoes and only written to contas_pagar on explicit confirmation, and any saved edit sends the bill back to pendente_conferencia, so unreviewed data never reaches payment.
- Telegram payment receipts (comprovante) are detected by the `comprovante_pagamento` flag in the shared extraction schema and NEVER create a new bill: pure matching in _shared/contasPagarComprovanteRegras.ts attaches the file to an open bill in the same unit (comprovante_url) and settles it with baixa_origem='telegram_comprovante'; ambiguous matches ask via cpv: buttons and senders without linked financeiro access get the attachment only, no settlement.
- Payroll (Folha) is fully independent of Contas a Pagar: writes go only through the folha-operacoes function and service-role folha_* functions, calculations use explicit folha_config values with no defaults, and exporting a Clara batch never marks payments, so payroll can never create, settle or alter payables.
- Payroll and allowance access restrictions must be enforced by the shared server permission functions as well as the presentation gate, so direct table access, uploads and service-mediated operations cannot bypass a temporary lock; retain stored grants for controlled restoration.
- Payroll month preparation only inserts missing folha_lancamentos rows with empty dados (upsert ignore-duplicates), so fixed values always come from the employee record and nothing variable is copied between months.
- Monthly cost allowance (Ajuda de Custo) has a single source table with its own closing, independent from the salary closing; legacy allowance parcels generated by salary closings stay valid and block a second allowance for the same unit/month.
